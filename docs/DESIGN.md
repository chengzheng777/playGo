# playGo · 设计与可行性评估

> 版本 v0.1 · 2026-11-05 · 状态：设计评审
>
> 目标：判断「PC 本地起服务 + 手机扫码加入 + 局域网/蓝牙通讯」在纯 Web 下是否成立，并给出通讯层（M0）的落地方案。

---

## 0. 结论

| 问题                           | 结论                                                             |
| ------------------------------ | ---------------------------------------------------------------- |
| 纯 Web 能否实现？              | ✅ 能，走 WiFi 局域网                                            |
| 蓝牙能否作为通道？             | ❌ 不能。浏览器无法做 BLE 外设广播，iOS 根本不支持 Web Bluetooth |
| 手机扫码加入？                 | ✅ 能。二维码里放局域网 URL，用**系统相机**扫，全程不需要 HTTPS  |
| 本地服务跑在哪？               | 原生进程（Node.js）；浏览器只做客户端，不能当服务器              |
| 推荐技术栈                     | Node + `ws` + 静态前端；实时性要求高再叠 WebRTC DataChannel      |
| 实时性上限（WebSocket/局域网） | 同网段往返 1–10 ms，30–60 Hz 状态同步无压力                      |

一句话：**「PC 当服务器 + 浏览器当客户端 + 二维码当发现机制 + WebSocket 当通道」完全可行；蓝牙这条线在浏览器里是死路，建议直接砍掉。**

## 2. 先定产品形态（直接影响协议）

「Web 电脑游戏 + 手机扫码」通常有两种形态，设计上都要能装下：

### 形态 A：大屏 + 手机手柄（Jackbox 式）

PC 屏幕是公共视图（棋盘、比分、动画），手机只显示私有信息（手牌、按钮、投票）。
→ 服务端必须**按角色裁剪视图**，不能把全量状态广播给所有人（否则偷看）。

### 形态 B：每台设备都是完整客户端

PC 和手机各自渲染完整画面，服务端只做权威状态与广播。
→ 状态同步量更大，但对裁剪无要求。

**统一抽象**：`role: "screen" | "player" | "spectator"`，服务端对每个连接下发 `view`，客户端不假设自己能拿到全量状态。M0 先按形态 A 跑通，形态 B 只是多下发一份数据。

## 3. 浏览器到底能跑什么「服务」

这是整个方案的地基，先把它说死：

| 想做的事                     | 浏览器内 | 说明                                                     |
| ---------------------------- | -------- | -------------------------------------------------------- |
| 监听 TCP 端口 / 开 HTTP 服务 | ❌       | 没有 Socket API。Direct Sockets 仅 ChromeOS 隔离应用可用 |
| UDP 广播 / mDNS 自动发现     | ❌       | 同上。`.local` 只能依赖操作系统解析，不可控              |
| 作为 BLE 外设广播            | ❌       | Web Bluetooth 只有 central 角色，没有 advertising API    |
| 连接 BLE 设备                | ⚠️ 部分  | Chrome 桌面 / Android，需 HTTPS，仅 GATT                 |
| P2P 数据通道                 | ✅       | WebRTC DataChannel，但需要信令通道                       |
| 拦截同源请求                 | ⚠️       | Service Worker，需 HTTPS                                 |
| 同机跨标签通信               | ✅       | BroadcastChannel / SharedWorker（仅同一台机器）          |
| WebSocket 客户端             | ✅       | 任意 http 页面都能连 `ws://`                             |
| 摄像头扫码                   | ⚠️       | `getUserMedia` 需 HTTPS；`BarcodeDetector` 仅部分浏览器  |

**结论**：浏览器只能做「客户端 + UI」。所谓「本地服务」必须由原生进程提供；浏览器里唯一接近 P2P 的能力是 WebRTC，而它仍然需要一条信令通道。因此服务端不可省，只能决定它跑在哪台机器上（本项目：房主的 PC）。

## 4. 通道方案对比

| 方案                             | 链路             | 延迟       | 需要 HTTPS                                   | 跨平台              | 复杂度 | 结论                            |
| -------------------------------- | ---------------- | ---------- | -------------------------------------------- | ------------------- | ------ | ------------------------------- |
| **A. 本机 HTTP + WebSocket**     | TCP / 局域网     | 1–10 ms    | 否                                           | 全平台              | 低     | ✅ **主方案**                   |
| B. 本机信令 + WebRTC DataChannel | UDP / 局域网直连 | <1–5 ms    | DataChannel 本身通常可用，媒体采集必须 HTTPS | 全平台              | 中     | 备选（实时动作 / 降服务器压力） |
| C. Web Bluetooth                 | BLE GATT         | 20–100 ms+ | 是                                           | 仅 Chrome / Android | 高     | ❌ **不可行**，见 4.1           |
| D. 纯 P2P 扫码互换 SDP           | UDP              | 低         | 是（要开摄像头）                             | 需双端摄像头        | 高     | ❌ 体验差，仅作无服务端兜底     |

### 4.1 为什么蓝牙不行

1. **角色不对**：Web Bluetooth 只允许浏览器作为 central 去连已有的 GATT 外设（`requestDevice()` → `connect()`）。PC 浏览器无法「被手机发现」——没有 advertising / peripheral API。[MDN: Web Bluetooth API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Bluetooth_API)
2. **平台缺失**：iOS Safari 完全不支持；Firefox 不支持。桌面端只有 Chromium 系可用。
3. **门槛高**：必须在安全上下文（HTTPS）下运行，局域网自签证书会劝退所有人。
4. **性能不对**：GATT 通知的吞吐和延迟（几十 ms、KB/s 级）不适合游戏状态同步，连传个棋盘都勉强。

**如果非要用蓝牙**：只能上原生壳（Electron + `bleno` 做外设 / Tauri + 原生插件），且 BLE 只负责传「WiFi 名称 + 密码 + 房间 token」，真正的数据仍然走 WiFi。复杂度翻倍、收益接近零 → **列为非目标**。

### 4.2 什么时候再上 WebRTC

- 游戏是实时动作类（>10 Hz 状态、要求 <50 ms）；
- 或想做成 mesh，减轻房主 PC 的广播压力；
- 或未来要跨公网（此时才需要 STUN/TURN）。

局域网内 ICE 的 host candidate 就能直连，不需要 STUN/TURN。信令直接复用本机 WebSocket。**M0 不上，等游戏类型确定后再评估。**

## 5. 最大的坑：安全上下文

| 能力                       | `http://localhost` | `http://192.168.x.x` |
| -------------------------- | ------------------ | -------------------- |
| 页面 / WebSocket           | ✅                 | ✅                   |
| `getUserMedia`（摄像头）   | ✅                 | ❌                   |
| Web Bluetooth / NFC        | ✅                 | ❌                   |
| Service Worker（PWA 离线） | ✅                 | ❌                   |
| Wake Lock（防息屏）        | ✅                 | ❌                   |
| `navigator.share`          | ✅                 | ❌                   |

局域网 IP 的 http 页面**不是**安全上下文。所以：

- 手机端页面**不要**依赖上述任何 API；
- 扫码用**系统相机**（不经过网页），加入页只做「输昵称 + 连 WS」；
- 想让页面内扫码，就得上 HTTPS：mkcert 自签 + 手机装根证书（Android 可用，iOS 要描述文件 + 完全信任）、公网域名 + 隧道（要外网）、或 Chrome 启动参数（仅开发机）。三条路都不适合「发给朋友扫一下就能玩」。

**因此：全站 http，扫码交给系统相机。这是本项目最重要的取舍。**

## 6. 推荐架构

```
┌──────────────────────────── PC ────────────────────────────┐
│                                                            │
│  ┌──────────────┐        ┌──────────────────────────────┐  │
│  │ PC 浏览器     │  HTTP  │  Node 本地服务                │  │
│  │ 房主 / 大屏   │◄──────►│  · 静态资源 / 加入页          │  │
│  │ localhost    │   WS   │  · 房间管理（内存）           │  │
│  └──────────────┘        │  · WebSocket 广播             │  │
│                          │  · 二维码 / 网卡枚举          │  │
│                          └──────────────┬───────────────┘  │
│                                         │ 监听 0.0.0.0:8787 │
└─────────────────────────────────────────┼──────────────────┘
                                          │ WiFi 局域网
                          ┌───────────────┴───────────────┐
                   ┌──────▼──────┐                 ┌──────▼──────┐
                   │ 手机 A 浏览器│                 │ 手机 B 浏览器│
                   │ 扫码 → 手柄  │                 │ 扫码 → 手柄  │
                   └─────────────┘                 └─────────────┘
```

| 组件       | 职责                                               | 备注                                   |
| ---------- | -------------------------------------------------- | -------------------------------------- |
| Node 服务  | 静态文件、REST、WS、房间状态机、二维码、网卡枚举   | 单进程，内存存房间，不落盘             |
| PC 浏览器  | 房主 UI + 大屏视图                                 | `localhost` 属安全上下文，可用全部 API |
| 手机浏览器 | 扫码进入的加入页 + 手柄视图                        | 只用表单 + WS，不碰敏感 API            |
| 二维码     | 发现机制，内容为 `http://<LAN-IP>:<port>/j/<code>` | 系统相机直接打开                       |

**端口策略**：默认 8787，被占用则 8787–8797 顺延，实际端口写进二维码。HTTP 与 WS 同端口、同源，避免 CORS 与混合内容问题。

## 7. 加入流程

```
PC 浏览器              本机 Node 服务                 手机浏览器
    │  POST /api/rooms      │                             │
    │──────────────────────►│                             │
    │  {code, urls[], token}│                             │
    │◄──────────────────────│                             │
    │  WS /ws  (role=screen)│                             │
    │──────────────────────►│                             │
    │                       │                             │
    │  显示二维码 http://192.168.1.23:8787/j/7K2M         │
    │                       │◄──── 系统相机扫码打开 ───────│
    │                       │◄──── GET /j/7K2M ───────────│
    │                       │───── 加入页 HTML ──────────►│
    │                       │◄──── WS room.join ──────────│
    │◄──── room.state ──────│───── room.state ───────────►│
    │                       │                             │
    │  点「开始」            │                             │
    │──────────────────────►│───── game.start ───────────►│
    │◄──── game.state ──────│───── game.state ───────────►│
```

关键点：

1. 二维码里的 IP 必须是**局域网 IP**，绝不能是 `127.0.0.1`；
2. PC 自己走 `localhost`，手机走 LAN IP，两者是不同 origin，但连的是同一个服务；
3. 加入页**不需要**先知道房间码——房间码在 URL 路径里，页面自动带上来。

## 8. 局域网里的 12 个坑

| #   | 现象                        | 原因                                                           | 对策                                               |
| --- | --------------------------- | -------------------------------------------------------------- | -------------------------------------------------- |
| 1   | PC 能打开，手机打不开       | 二维码用了错误网卡 IP（VPN / Docker / WSL / Hyper-V 虚拟网卡） | 枚举网卡，过滤虚拟网卡，房主手动选，二维码实时刷新 |
| 2   | 手机第一次连不上            | Windows 防火墙拦截 Node 入站                                   | 首次监听弹窗勾选「专用网络」；文档给出放行命令     |
| 3   | 页面能开，WS 连不上         | 路由器开了 AP 隔离 / 访客网络                                  | 提示切到主网络或手机热点                           |
| 4   | 一直转圈                    | 手机连的是 5G 蜂窝，不在同一网段                               | 加入页检测并提示                                   |
| 5   | 时好时坏                    | 2.4G/5G 不同 SSID、中继、电力猫                                | 尽量同 SSID、靠近路由器                            |
| 6   | 公司/校园网连不上           | 网络策略禁止客户端互访                                         | 手机热点（PC 连手机，或手机连 PC 热点）            |
| 7   | 端口被占用                  | `EADDRINUSE`                                                   | 自动顺延端口并写回二维码                           |
| 8   | 手机锁屏回来白屏            | WebSocket 被系统挂起断开                                       | 心跳 + 指数退避重连 + 状态 resync（座位保留 90s）  |
| 9   | iOS 切后台丢消息            | Safari 后台挂起                                                | 同上；关键操作要求前台确认                         |
| 10  | 二维码扫出来是 localhost    | 用了 `window.location.hostname`                                | 二维码永远用服务端探测到的 LAN IP                  |
| 11  | 页面是 https 却连不上 ws:// | 混合内容被浏览器拦截                                           | 全站统一 http；未来上 https 就必须同步 wss         |
| 12  | 同一 WiFi 但跨网段          | 路由器双 NAT / 中继模式                                        | 提示换网；不做自动穿透                             |

## 9. 通讯协议

见 [PROTOCOL.md](./PROTOCOL.md)。M0 只实现：建房、加入、全量房间状态广播、聊天、心跳、断线重连。

设计要点：

- **服务端权威**：所有状态变更由服务端计算后广播，客户端只发意图；
- **全量快照 + version**：M0 房间人数少，直接全量，简单不易错；后续再改增量；
- **按角色裁剪**：`screen` / `player` / `spectator` 拿到的 `view` 不同；
- **不用帧同步**：浏览器 JS 浮点与时钟不一致，锁步会漂移；用状态同步。

## 11. 里程碑

| 阶段            | 内容                                                   | 验收                 |
| --------------- | ------------------------------------------------------ | -------------------- |
| **M0 通讯打通** | 建房、二维码、手机加入、房间广播、聊天、重连           | 见下方清单           |
| M1 房间大厅     | 昵称/头像、准备、踢人、房主转移、本机房间列表          | 3 台设备稳定进出     |
| M2 游戏骨架     | 权威状态机、回合、动作校验、视图裁剪、快照/重连恢复    | 换一个游戏只改规则层 |
| M3 首个游戏     | 选一个规则简单的（猜词/你画我猜/狼人杀）               | 完整一局             |
| M4 分发体验     | 单 exe、托盘、自动开浏览器、错误自检（防火墙/AP 隔离） | 非开发者能独立开局   |

### M0 验收清单

1. PC 执行 `pnpm dev`，浏览器自动打开 `http://localhost:8787`，点「创建房间」出现二维码。
2. 手机（同一 WiFi）用系统相机扫码，打开加入页，输昵称后进入大厅；PC 端 1 秒内看到该玩家。
3. 两台手机同时加入，互相可见。
4. 手机发聊天消息，PC 与另一台手机实时收到（局域网 <100 ms）。
5. 手机关屏 30 秒再打开，自动重连，座位与昵称恢复。
6. 拔掉 WiFi 再连回，PC 端在 15 秒内标记该玩家「掉线」，重连后恢复。
7. 切换网卡选择，二维码地址随之变化，新地址可被手机打开。
8. 端口 8787 被占用时自动换端口，二维码同步更新。

## 13. 待确认

1. **游戏类型与实时性**：回合制（卡牌、桌游、猜词）还是实时动作？前者 M0 的 WebSocket 足够，后者要在 M2 前决定是否上 WebRTC。
2. **形态 A 还是 B**：手机是「手柄 / 私有信息」还是「完整游戏画面」？影响协议里的视图裁剪。
3. **目标手机**：iOS 占比多少？iOS 的 WebSocket 后台挂起最严重，重连策略要按最差情况设计。
4. **是否需要完全离线**：若要求无外网也能玩，就不能用 CDN、字体、任何远程依赖，全部本地打包。
