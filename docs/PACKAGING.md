# 打包与分发

> 回答两个问题：能不能打成一个客户端包？纯网页部署能不能本地跑？

---

## 0. 一句话

**能，而且应该打成一个包——但只打 PC 房主端。手机端永远不装任何东西，扫码即用。**

这正是这套架构相对原生 App 的最大优势：安装成本只落在一个人（房主）身上，且是一次性的。

---

## 1. 为什么纯网页不能「本地跑」

「网页部署 + 浏览器打开」这条路走不通，不是实现问题，是浏览器安全模型的硬边界：

| 硬限制 | 说明 |
| --- | --- |
| 不能监听端口 | 浏览器没有 TCP/UDP Socket API，无法接受手机发来的连接 |
| 不能起进程 | 没有 spawn/exec，起不了 Node、也起不了任何本地程序 |
| 不能读本地文件当服务 | `file://` 是独立源，连 fetch 同目录的 JSON 都会被 CORS 拦 |
| Service Worker 不是服务器 | 只能拦截**自己源**的请求，不能接外部入站连接 |
| WebRTC 也要信令 | 就算 P2P，双方仍要先交换 SDP；没有服务端就得手动互扫二维码，且 PC 还得有摄像头 + HTTPS |

结论：**浏览器只能当客户端。** 想「本地跑」，就必须有一个原生进程；问题只剩「这个进程怎么送到用户手上」。

顺带澄清一个常见混淆：

- **部署到公网服务器** = 中心化模式，房间跑在云上，玩家不在同一局域网也能玩，但要外网、要服务器成本；
- **本地服务** = 每台 PC 自己跑，离线可用、零延迟、零成本。

两者是不同产品，不能靠「网页部署」互相替代。

## 2. 四种交付形态

| 形态 | 用户要做什么 | 需要外网 | 流量路径 | 客户端感 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **A. 单文件 exe + 系统浏览器** | 下载 → 双击 | ❌ | 全部局域网 | 中（可用 Edge `--app` 去地址栏） | ✅ **推荐** |
| B. Electron / Tauri 套壳 | 下载 → 安装 | ❌ | 全部局域网 | 强（独立窗口、托盘、全屏） | 后期可选 |
| C. 公网网页 + 云信令 + WebRTC | 打开链接 | ✅ | 信令走云，数据走局域网 P2P | 弱 | 想做「零安装分享」时再考虑 |
| D. 纯网页 + 无服务端 | 手动互扫 SDP | ✅ | P2P | 不可用 | ❌ |

**推荐 A**：一个 exe，双击后自动起服务并打开浏览器。用户感知上就是个客户端，但技术上是「本地服务器 + 系统浏览器」，包体小、构建简单、浏览器永远是最新版。

## 3. 单文件里装了什么

```
playGo.exe
├── Node/Bun 运行时          （编译进二进制）
├── 服务端代码               （esbuild 打成单文件 JS）
│   ├── Fastify / 静态资源
│   ├── ws 房间管理
│   └── 二维码生成
└── 前端产物 dist/           （HTML/JS/CSS/字体，构建期内嵌）
```

运行时行为：

```
双击 exe
  └─ 探测 8787–8797 可用端口
       ├─ 已有实例在跑？→ 直接打开浏览器，退出
       └─ 起服务 → 打开 http://localhost:<port> → 页面显示二维码
```

**注意**：exe 只是「服务器 + 启动器」，游戏画面仍在浏览器里渲染。这也是为什么手机端不需要装包——它只是访问同一个 HTTP 服务。

## 4. 打包技术选型

| 方案 | 体积 | 构建难度 | 跨平台 | 内嵌前端 | 成熟度 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **Bun `--compile`** | 40–90 MB | 低 | win/mac/linux | ✅ `with { type: "file" }` | 高 | ✅ **首选** |
| **Node SEA** | 70–110 MB | 中 | 全平台 | ✅ `sea.getAsset()` | 中（22+ 更稳） | ✅ 备选 |
| `pkg` | 40–60 MB | 低 | 全平台 | ✅ | ❌ 已归档不维护 | ❌ 不用 |
| Deno `compile` | 80–120 MB | 中 | 全平台 | ✅ | 中 | 备选 |
| Electron | 120–200 MB | 中 | 全平台 | ✅ | 高 | 需要托盘/自动更新时 |
| Tauri 2 | 3–15 MB | 高 | 全平台 | ✅ | 高 | 服务端要改 Rust，或挂 sidecar |
| `npx playgo` | 0 | 最低 | 全平台 | ✅ | — | 只给有 Node 的人 |

体积差异主要来自「运行时有多大」：Bun/Node 自带整个 JS 引擎，所以几十 MB 起步；Tauri 复用系统 WebView 才几 MB，但服务端得用 Rust 重写（或塞一个 Node sidecar，又回到几十 MB）。

**建议**：M0–M3 用 `pnpm dev`，不打包；M4 用 Bun compile 出 exe。理由：打包会拖慢迭代，真机联调时跑源码比反复出包快得多。

## 5. 构建流水线

```
pnpm build
  ├─ vite build                     → dist/（前端）
  ├─ node scripts/embed-assets.ts   → src/generated/assets.ts（把 dist 打进代码）
  ├─ esbuild src/server/index.ts    → build/server.mjs（单文件）
  └─ bun build --compile            → playGo.exe
```

把前端产物**转成 TS 模块**再打进 bundle，而不是依赖各打包器的 asset API——这样 Bun / SEA / Deno 三种方案都能用同一份代码，迁移成本为零。前端资源用 base64 或字符串内联，体积会涨约 33%，但省掉一堆路径问题。

## 6. 打包后的 8 个坑

| # | 坑 | 表现 | 对策 |
| --- | --- | --- | --- |
| 1 | 黑框控制台 | 双击弹出 cmd 窗口 | 保留（能看到日志）；或编成 GUI 子系统，日志写文件 |
| 2 | SmartScreen | 「Windows 已保护你的电脑」 | 代码签名证书；或文档说明「更多信息 → 仍要运行」 |
| 3 | 杀软误报 | 自解压型二进制常被拦 | 用主流方案、提交白名单；别用已停维护的 pkg |
| 4 | 重复双击 | 第二个实例端口冲突 | 先探测 `/api/health`，有实例就只开浏览器 |
| 5 | 端口被占 | 起不来 | 8787–8797 顺延，二维码用实际端口 |
| 6 | 防火墙 | 手机连不上 | 首次监听弹窗勾「专用网络」；文档给放行命令 |
| 7 | 资源路径 | `__dirname` 在二进制里失效 | 全部资源走内嵌模块，不读磁盘 |
| 8 | 跨平台 | 以为一个包通吃 | win / mac / linux 各出一个包；mac 还需公证 |

另外，「像客户端」不一定要 Electron：Windows 上用 `msedge --app=http://localhost:8787` 打开，就是一个没有地址栏的独立窗口，零额外体积。

```powershell
start msedge --app=http://localhost:8787
```

## 7. Electron 还是 Tauri

### 7.1 结论

**这个项目选 Electron。** 决定性理由只有一条：**服务端是 Node。**

Electron 主进程本身就是 Node，`Fastify + ws` 原样搬进去就能跑，`0.0.0.0:8787` 照常监听，前端一行不改。
Tauri 的后端是 Rust，接不上这套 Node 服务，只有三条路，每条都要付代价：

| Tauri 的接法 | 做法 | 代价 | 包体积 |
| --- | --- | --- | --- |
| ① Rust 重写服务端 | axum + tokio-tungstenite | 房间逻辑、协议、校验写两遍；TS 类型共享断裂；开发速度减半 | 5–15 MB |
| ② Node sidecar | `externalBin` 塞一个 node 二进制 | 管子进程生命周期、端口发现、退出清理；孤儿进程风险 | 50–90 MB |
| ③ 只保留静态前端 | Rust 起个静态服务 | 等于方案 ①，房间逻辑仍要 Rust | 5–15 MB |

方案 ② 的包体积已经和 Electron 差不多了，却多了「进程管理」这一整类 bug。方案 ① 等于把最核心的业务逻辑用不熟的语言重写。**两种都不划算。**

### 7.2 针对本项目的加权对比

| 维度 | Electron | Tauri 2 | 对本项目权重 |
| --- | --- | --- | --- |
| 服务端落地 | 主进程直接跑 Node，零改动 | Rust 重写 / sidecar | ⭐⭐⭐ |
| 语言栈 | 全 TypeScript | Rust + TS | ⭐⭐⭐ |
| 构建环境 | 只要 Node | Rust + MSVC + WebView2 SDK | ⭐⭐ |
| 加载 `http://localhost` 后的原生能力 | preload 正常注入，无限制 | 需在 capabilities 里配 `remote.urls` 才放行 IPC | ⭐⭐ |
| 渲染一致性 | 自带 Chromium，版本固定 | 系统 WebView2，版本随系统更新 | ⭐⭐ |
| 调试 | DevTools 完整 | 需手动开启，链路弱 | ⭐⭐ |
| 生态与踩坑资料 | 极多 | 较少 | ⭐⭐ |
| 包体积 | 120–200 MB | 5–15 MB（+WebView2 运行时） | ⭐ |
| 内存 / 启动 | 150–300 MB / 1–2 s | 60–120 MB / <1 s | ⭐ |
| 自动更新 | electron-updater | 内置 updater（要签名密钥） | ⭐ |
| 未来做 BLE | `noble` 已停维护 | `btleplug` 活跃 | ⭐ |

体积和内存这一列 Tauri 赢得很干脆，但对一个「发给几个朋友、局域网玩」的游戏来说，100 MB 和 10 MB 的差别远不如「少写一遍服务端」值钱。

### 7.3 什么情况下反过来选 Tauri

- 包体积 / 启动速度变成硬指标（要上架、要频繁分发）；
- 服务端愿意用 Rust 重写（长期看其实更稳，单二进制、无运行时依赖）；
- 蓝牙需求复活——Rust 的 `btleplug` 能真正做 BLE 外设，Electron 这边基本没戏；
- 想同时出移动端（Tauri 2 支持，但本项目手机走浏览器，用不上）。

### 7.4 好消息：这个决定可以推迟，而且不锁死

桌面壳只是「最外面那一层窗口」。因为 UI 本来就是普通网页、服务端是普通 HTTP 服务，换成 Electron 或 Tauri 时，**服务端和前端代码都不用动**，只是把 `start msedge --app=...` 换成 `new BrowserWindow({ loadURL: "http://localhost:8787" })`。

所以：

- **M0–M3**：两个都不上，`pnpm dev` + 系统浏览器；
- **M4 想要客户端感**：先试 Edge `--app`（零成本），不够再套 Electron；
- **将来真需要托盘 / 自动更新 / 更小体积**：再评估 Tauri，那时也只需替换外壳。

---

## 8. 结论

1. 打成一个包：✅ 可以，且推荐。
2. 只打 PC 房主端：✅ 手机端零安装是核心卖点。
3. 纯网页本地跑：❌ 不可能，浏览器没有监听端口的能力。
4. 现在的动作：**不打包**，先做 M0 通讯；M4 再用 Bun compile 出单文件 exe + Edge `--app` 模式。
5. 非要套壳：**Electron**（服务端零改动）；Tauri 留给「Rust 重写服务端」或「蓝牙复活」那天。
